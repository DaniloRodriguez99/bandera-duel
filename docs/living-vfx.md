# Living fire and ability lighting

`TorchEffects(scene, lighting)` accepts `setSources([{id, x, y, scale?}, ...])`; x/y is the flame's base, in world coordinates. Call `update(time, delta)` every frame and `destroy()` at teardown. Source definitions can include every terrain ember on a large map: camera culling happens before lighting registration, and only the nearest 64 candidate sources receive pooled flame sprites. The controller keeps 64 reusable sprites and one native emitter with 64 reserved spark particles. Removed sources immediately release their light IDs. `sources` exposes the retained definitions, and `diagnostics` exposes active frame, position, radius and intensity for inspection.

The eight original procedural 16 × 20 pixel frames change tongue height, width and curvature. Each source gets a stable ID-derived phase. Its visible flame, light position, radius and intensity share that phase, producing correlated variation without synchronized torches. A normal source has radius approximately 115–141 world units and nominal intensity 1; the lighting renderer applies global intensity. Scale can distinguish tiny terrain embers, torches, campfires and forges. Lower quality retains the six nearest torch lights before budgeting extra sources; it reduces flame frame rate and disables sparks. Reduced motion freezes shape/flicker and disables sparks, retaining illumination.

`AbilityLightingController(lighting)` exposes `sync(snapshot, now?)`, `event(event)`, `clear()` and `destroy()`. Call `setView(camera.worldView)` before syncing to reject offscreen candidates. Call `sync` once per rendered frame, and `event` once for each accepted new game event. `setProjectileSampler(arrow => renderedPosition)` lets the scene use precisely its own predicted projectile position. The default sampler uses shared `arrowMotion`, snapshot receipt age capped at 1/15 second, and paused-state behavior. Waves use shared `wavePoint` and the same age cap. No input, collision, damage, physics or network state is modified.

At most 32 tracked ability lights exist. Stable IDs cover magical projectiles, non-steel waves, black holes and visible living players' magical charges. Removed entities fade for 160ms, then their light IDs are removed; `clear()` removes all immediately. Scene reset must call `clear()`. Regular arrows and plain melee hits do not create illumination. Fire, ice, blood/shadow, wind, lightning and charged warrior attacks keep their existing color language; explicit event colors override defaults. Existing shared visibility checks prevent charge lighting from revealing concealed opponents. The controller's `diagnostics` lists its current bounded light records.

Both modules depend only on the structural lighting contract `setLight(id,{x,y,color,radius,intensity,falloff?})`, `removeLight(id)` and `flash(x,y,color)`. Cached pixel textures are reused across scene restarts. Resource counts above are allocation bounds, not measured frame-rate guarantees. Browser validation should inspect shape changes, correlated light variation, projectile alignment, map transitions and all quality presets at native gameplay zoom.

Idle weapons with an existing magical affinity glow and active awakened/reinforced states also receive a small local light (`ability:weapon:<playerId>`). Physical/earth affinity colors are excluded. `Snapshot.mobProjectiles` was audited: its only producer is the skeleton's ordinary arrow, and its schema contains no magical element. Those arrows deliberately remain unlit. Elemental world projectiles already arrive through `Snapshot.arrows.worldElement` and are covered there.
